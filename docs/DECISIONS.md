# 설계 결정 기록

이 문서는 llm-check에서 고른 도구와 설정이 **어떤 문제를 막기 위한 선택인지** 기록한다.
한 줄 요약: 이 도구는 LLM 출력 파일을 오프라인에서 검사하므로, 런타임 의존성을 0으로 두고
개발 단계의 안전망(타입·린트·테스트·CI)에 비용을 집중한다.

## 1. 왜 ESM인가

- Node 20 이상에서 ESM이 기본 모듈 형식이고, `node:util`의 `parseArgs`처럼 쓰려는 표준 API가 모두 ESM에서 바로 쓰인다.
- CJS/ESM을 섞으면 `__dirname` 유무, 조건부 export, `require` 불가 같은 문제를 계속 분기해야 한다.
  처음부터 ESM 하나로 고정해 그 분기를 없앴다.
- `import.meta.url`을 쓸 수 있어 "파일 기준 경로"를 번들 이후에도 안정적으로 계산할 수 있다(→ 7번).

## 2. 왜 tsup인가

- 필요한 건 "TS 한 덩어리를 실행 가능한 CLI 파일 하나로" 만드는 것뿐이다. tsup은 esbuild 래퍼라 설정 10줄로 그게 된다.
- CLI를 `tsc`로만 빌드하면 산출물이 파일 트리로 남아 `.js` 확장자·상대경로 문제를 신경 써야 하고, shebang을 붙일 방법이 없다.
  tsup은 번들 + shebang 주입을 한 번에 해 준다.
- rollup/webpack은 이 규모에서 설정 비용이 더 크고, 라이브러리 배포(d.ts, 다중 포맷)가 목표가 아니라 과하다.
- shebang은 소스가 아니라 `banner`로 번들에만 붙인다. 소스에 두면 번들러 설정에 따라 사라지거나 중복될 수 있고,
  실행 파일은 어차피 `dist/cli.js` 하나다.

## 3. 왜 `node:util`의 `parseArgs`인가

- `--help` / `--version` 두 개뿐인 CLI에 외부 파서를 넣으면, 의존성 트리와 공급망 위험이 기능 대비 과하다.
- `parseArgs`는 Node 18.3+ 표준이고 `strict: true`에서 모르는 옵션을 던져 주므로, 오타(`--versoin`)가 조용히 무시되지 않는다.
- 결과적으로 **런타임 의존성 0개**가 유지된다. 오프라인 검사 도구에서 이건 그 자체로 기능이다(설치가 가볍고 재현이 쉽다).
- 서브커맨드가 필요해지면 `allowPositionals`를 켜고 `src/commands` 아래로 분기하면 된다. 그 지점이 오면 다시 판단한다.

## 4. 왜 ESLint flat config + typescript-eslint strictTypeChecked인가

- flat config(`eslint.config.js`)는 ESLint 9+의 기본이고, `.eslintrc` 계열의 암묵적 상속·플러그인 해석 문제를 없앤다.
- 설정 파일을 `.ts`가 아니라 `.js`로 둔 이유: TS 설정 파일을 읽히려면 추가 로더 의존성이 필요하다. 그걸 피했다.
  대신 `eslint.config.js`는 타입 인식 규칙 대상(`**/*.ts`)에서 빠지므로 사실상 린트되지 않는다. 파일이 짧아 감수한다.
- `strictTypeChecked`를 고른 건 이 프로젝트가 **외부에서 온 신뢰할 수 없는 JSON**(LLM 출력)을 다루게 되기 때문이다.
  `no-unsafe-assignment`, `no-unsafe-member-access` 같은 타입 인식 규칙이 "파싱 결과를 검증 없이 쓰는" 코드를 컴파일 전에 잡아 준다.
- 타입 인식 규칙은 타입 정보가 필요하므로 `parserOptions.projectService: true`와 `tsconfigRootDir`가 필수다.
  `projectService`는 tsconfig를 IDE와 같은 방식으로 찾아 주므로, 파일 목록을 린트 설정에 중복 관리하지 않아도 된다.
- `any` 금지는 `strictTypeChecked`에 이미 포함되지만, 프로젝트 규칙이라 `no-explicit-any`를 명시해 의도를 드러냈다.

## 5. 왜 Vitest인가

- TS와 ESM을 추가 변환 설정 없이 그대로 실행한다. Jest는 ESM + TS 조합에서 transform/moduleNameMapper 설정이 늘어난다.
- `node --test`는 의존성이 0이지만 TS를 직접 실행할 수 없어 별도 로더가 필요하고, 이 프로젝트는 "순수 함수에 대한 입력/출력 단정"을
  많이 쓰게 될 예정이라 watch·필터링이 편한 쪽이 낫다.
- `vitest.config.ts`는 **만들지 않았다**. 기본 include 패턴이 `test/*.test.ts`를 이미 잡으므로 빈 설정 파일은 노이즈다.
  커버리지나 환경 설정이 필요해지는 시점에 추가한다.

## 6. 왜 strict / noUncheckedIndexedAccess / exactOptionalPropertyTypes인가

- `strict`: null·undefined를 타입으로 다루지 않으면, 검사 도구에서 가장 흔한 버그인 "필드가 없는 입력"에서 바로 깨진다.
- `noUncheckedIndexedAccess`: 이 도구는 배열·레코드 인덱싱을 많이 하게 된다(`items[0]`, `record[key]`).
  이 옵션이 없으면 TS는 비어 있는 입력에도 값이 있다고 가정한다. 켜 두면 인덱싱 결과가 `T | undefined`가 되어
  "LLM이 빈 배열을 돌려준 경우"를 컴파일 시점에 처리하게 강제한다.
- `exactOptionalPropertyTypes`: `{ reason?: string }`에 `undefined`를 명시적으로 넣는 것과 키를 생략하는 것을 구분한다.
  검사 결과를 JSON으로 출력할 때 `"reason": undefined`가 섞이면 직렬화 결과가 달라지므로, 그 차이를 타입으로 묶어 둔다.

### 함께 켠 옵션 (덜 알려진 것들)

- `module`/`moduleResolution: NodeNext`: Node의 ESM 해석 규칙(확장자 필수, `exports` 필드)을 TS가 그대로 검사하게 한다.
  이걸 켜면 `import "./core/help.js"`처럼 **`.js` 확장자를 붙여야** 한다. 소스는 `.ts`인데 `.js`를 쓰는 게 어색해 보이지만,
  런타임이 보는 경로를 그대로 쓰는 것이 맞다(번들러 없이 실행해도 깨지지 않는다).
- `verbatimModuleSyntax`: `import type`을 자동으로 지우지 않고 작성한 그대로 내보낸다.
  타입만 쓰는 import가 런타임 import로 남아 부수효과를 일으키는 사고를 막는다.
- `isolatedModules`: 파일 하나만 보고 변환할 수 있는 코드만 허용한다. esbuild(tsup)가 파일 단위로 변환하므로,
  "tsc는 통과하는데 번들은 깨지는" 조합을 미리 차단한다.
- `types: ["node"]`: 설치된 모든 `@types`를 자동으로 끌어오지 않고 Node 타입만 명시한다. 전역 타입이 의도치 않게 섞이는 걸 막는다.
- `noEmit: true`: 빌드는 tsup이 하고 tsc는 검사 전용이라는 역할 분리를 설정에 박아 둔다. 그래서 `npm run typecheck`가 산출물을 만들지 않는다.
- `skipLibCheck: true`: 의존성의 `.d.ts`까지 검사하지 않는다. 우리 코드 문제만 보려는 것이고, 검사 시간도 짧아진다.

## 7. 왜 `core/`를 CLI와 분리했는가

- 검사 로직(`core`)은 "입력 문자열 → 판정 결과"인 순수 함수로 두면 테스트에 파일도 프로세스도 필요 없다.
  LLM 출력 검사기는 경계 조건이 많아서, 테스트 비용이 설계 품질을 그대로 결정한다.
- `process.exit`, `console`, `fs` 같은 Node 전용 코드가 로직에 섞이면 테스트가 프로세스 종료나 stdout 캡처에 묶인다.
  그래서 I/O는 `src/commands`, 출력·인자 해석은 `src/cli.ts`로 몰았다.
- 같은 로직을 나중에 CI 플러그인이나 다른 실행 형태에서 재사용할 길도 열어 둔다.
- 구체적인 예: `src/core/version.ts`는 package.json **텍스트**에서 version을 뽑는 순수 함수이고,
  파일을 읽는 쪽은 `src/commands/version.ts`다.

## 8. `--version`을 package.json에서 읽는 이유와 경로 규칙

- 버전 문자열을 코드에 상수로 두면 `package.json`과 어긋난다. 단일 출처를 유지하려고 실행 시점에 `package.json`을 읽는다.
- 경로는 `src/cli.ts`에서 `new URL("../package.json", import.meta.url)`로 계산한다.
  `src/cli.ts`와 번들 산출물 `dist/cli.js`가 **둘 다 패키지 루트의 한 단계 아래**라서 같은 상대 경로가 양쪽에서 유효하다.
  (경로 계산을 `src/commands/` 안에서 하면 번들 후 깊이가 달라져 깨진다. 그래서 진입점이 계산해 인자로 넘긴다.)
- 대안으로 빌드 시 버전을 문자열로 주입(`define`)할 수도 있지만, 그러면 빌드 없이 소스를 실행할 때 값이 비어 버린다.

## 9. 왜 GitHub Actions에서 `npm ci` + `npm run check`인가

- `npm ci`는 `package-lock.json`을 **그대로** 설치한다(없거나 어긋나면 실패). `npm install`은 lock을 갱신할 수 있어
  "CI에서만 다른 버전이 설치돼 통과/실패가 달라지는" 상황이 생긴다. 재현 가능한 환경이 목적이므로 `ci`를 쓴다.
- `npm run check` 하나만 돌리는 이유: 로컬에서 치는 명령과 CI가 치는 명령이 같아야 "내 PC에서는 됐는데" 상황이 줄어든다.
  검사 항목이 늘어나도 수정할 곳은 `package.json`의 `check` 한 곳이다.
- `push`와 `pull_request` 둘 다에서 돌린다: 브랜치 작업 중에도 깨짐을 바로 보고, PR에서는 머지 기준 상태로도 확인한다.
- `cache: npm` 사용 이유: `actions/setup-node`가 lock 파일 해시로 npm 캐시를 복원해 설치 시간을 줄인다.
  캐시 키가 `package-lock.json` 해시라서 의존성이 바뀌면 자동으로 무효화되므로, `npm ci`의 재현성을 깨지 않는다.
- CI가 어떤 Node에서 도는지는 10번 절에서 따로 정리했다(검사는 22/24 매트릭스, Node 20은 산출물 실행만 검증).

## 10. Node 버전: 사용 조건과 개발 조건을 분리한다

관찰한 사실(설치된 버전의 `engines.node`):

| 패키지 | 요구 Node |
| --- | --- |
| `tsup@9.0.0` | `^22.18.0 \|\| ^24.11.0 \|\| >=26.0.0` |
| `vitest@5.0.5` | `^22.12.0 \|\| ^24.0.0 \|\| >=26.0.0` |
| `eslint@10.14.0` | `^20.19.0 \|\| ^22.13.0 \|\| >=24` |
| 우리 패키지(`engines`) | `>=20` |

즉 **개발 도구의 하한은 Node 22.18**인데 CI는 Node 20에서 돌고 있었다. 지금 깨지지 않더라도
지원 밖 버전에서 검사를 돌린 셈이고, 도구가 새 문법·API를 쓰기 시작하면 CI에서만 터진다.

- **`engines.node: ">=20"`은 유지한다.** 이 필드는 **빌드 산출물의 실행 조건**이다.
  `dist/cli.js`는 런타임 의존성이 0개이고 `node:util`의 `parseArgs`, `node:fs/promises`, `import.meta.url`만 쓰므로
  Node 20에서 문제없이 돈다. 개발 도구 사정 때문에 사용자에게 Node 22를 요구하는 것은 근거가 없다.
- **검사는 Node 22/24 매트릭스에서 돌린다.** 22는 개발 도구의 하한(22.18+)이고, 24는 그다음 LTS다.
  한 버전만 돌리면 "로컬은 24, CI는 22"처럼 버전 차이에서만 나는 문제를 놓친다.
  `node-version: "22"`는 22.x 최신 패치를 받으므로 tsup의 `^22.18.0` 하한을 만족한다(그래서 `22.18`로 고정하지 않았다).
  매트릭스에 20을 넣지 않은 이유: `npm ci`는 경고만 내고 통과하지만, 그 위에서 돌린 tsup/vitest 결과는 지원 밖이라 신뢰할 수 없다.
- **`runtime-floor` job이 따로 필요한 이유**: 위 매트릭스는 `engines`의 하한을 전혀 검증하지 않는다.
  산출물이 Node 20에서 안 돌면 `engines: ">=20"`은 거짓 광고가 된다. 그래서 빌드는 Node 22에서 하고,
  같은 job에서 `setup-node`를 한 번 더 호출해 **실행만 Node 20으로 바꿔** `--help`와 `--version`을 실제로 돌린다.
  job을 두 개로 쪼개면 `dist/`를 artifact로 올렸다 내려야 해서 더 복잡해진다.
- `--version` 출력은 `package.json`의 값과 **문자열 비교**해서 다르면 job을 실패시킨다.
  이 한 줄로 번들의 shebang, ESM 실행, `../package.json` 상대 경로(8번 절)가 Node 20에서도 유효한지 함께 확인된다.
- `.npmrc`의 `engine-strict`는 켜지 않았다. 켜면 Node 20 환경에서 devDependencies 설치 자체가 막혀
  `runtime-floor` job과 "Node 20 사용자" 시나리오가 둘 다 깨진다. 대신 이 구분을 README 표와 CI job 구성으로 드러냈다.

## 11. JSON 추출(`src/core/extract-json.ts`)

### 정규식 대신 상태 기반 스캔

- 정규식은 **중첩 깊이**를 셀 수 없고, **문자열 안의 괄호**를 구분하지 못한다.
  `{"feedback": "괄호 {가 들어간} 문장"}` 같은 입력에서 정규식 기반 매칭은 블록 경계를 틀리게 잡는다.
  LLM이 돌려주는 JSON은 사람이 읽을 문장을 값으로 담는 경우가 많아 이 상황이 예외가 아니라 일상이다.
- 그래서 (a) 여는 괄호 스택, (b) 문자열 내부 여부, (c) 백슬래시 이스케이프 세 상태만 들고 텍스트를 한 번만 훑는다.
  O(n) 한 번 통과이고, 동작을 한 화면 안에서 눈으로 검증할 수 있다.
- 코드펜스(```` ```json ````)는 **따로 처리하지 않는다**. 첫 여는 괄호부터 짝까지만 잘라내면 코드펜스는 자연히 블록 밖으로 빠진다.
  특수 케이스를 더하지 않고도 처리되는 것을 테스트로 고정해 두었다.

### 깨진 JSON을 고치지 않는 이유

- 따옴표 보정, 후행 쉼표 제거, 단일 따옴표 치환 같은 "복구"는 **원래 모델이 의도한 값과 다른 값**을 조용히 만들어 낼 수 있다.
  이 도구의 역할은 검사이므로, 잘못된 입력을 그럴듯하게 바꿔 통과시키는 것이 가장 나쁜 실패다.
- 블록도 **첫 번째 하나만** 찾는다. 여러 후보를 모아 "가장 잘 파싱되는 것"을 고르기 시작하면
  입력이 조금 달라질 때 결과가 뒤집히고, 왜 그 블록이 선택됐는지 설명할 수 없게 된다.
- 대신 실패를 세 가지로 나눠(`no-json` / `unbalanced` / `parse-error`) **무엇이 잘못됐는지는 정확히** 알려준다.
  고칠지 말지는 호출자가 결정할 문제다.

### 결과를 판별 유니온으로 둔 이유

- 실패를 예외로 던지면 호출자가 try/catch를 빼먹어도 컴파일러가 잡아 주지 못한다.
  반면 `ok` 필드로 판별되는 유니온은 `result.value`를 쓰기 전에 `result.ok` 검사를 **타입 수준에서 강제**한다.
  이 도구는 "실패가 정상 결과"인 검사기라서, 실패 경로가 타입에 드러나는 편이 맞다.
- `value`는 `unknown`이다. 추출 단계에서 모양을 단정하면 그 뒤 모든 코드가 근거 없는 타입을 신뢰하게 된다.
  검증은 다음 단계의 책임으로 분리했다.
- `start`는 `no-json`일 때 의미가 없어 **키 자체를 넣지 않는다**. `exactOptionalPropertyTypes`(6번 절)가 켜져 있어
  `start: undefined`를 넣는 것과 생략하는 것이 다른 타입이고, 이 구분이 "위치 정보가 있는 실패"와 "없는 실패"를 그대로 표현해 준다.

## 12. 스키마 검사(`src/core/schema.ts`, `src/core/validate.ts`)

### 왜 Zod가 아니라 JSON Schema의 부분집합인가

- 이 도구는 CLI라서 **사용자가 스키마를 파일로 넘긴다**. Zod는 코드로 쓰는 스키마이므로 사용자가 TS/JS 파일을 작성하고
  CLI가 그 파일을 import해 실행해야 한다. 검사 도구가 검사 대상의 설정 코드를 실행하는 구조는 피했다(임의 코드 실행 + 로더 문제).
- JSON Schema는 **데이터**라서 JSON 파일 하나로 끝나고, 다른 도구나 에디터와도 형식이 통한다.
- Zod는 런타임 의존성이기도 하다. 설치가 가벼운 오프라인 도구라는 성격(3번 절)과 맞지 않는다.

### 왜 ajv 같은 라이브러리 대신 직접 구현했는가, 그리고 한계

- 필요한 키워드가 적다. LLM 출력 검사는 대개 타입·범위·길이·개수·enum·필수 필드·추가 필드 금지로 충분하다.
  ajv는 전체 스펙과 런타임 코드 생성을 함께 들고 오는데, 그 비용 대비 쓰는 기능이 너무 적다.
- 직접 구현하면 **오류 메시지와 경로를 이 CLI의 출력 형식에 맞게** 만들 수 있다. ajv 메시지를 한국어로 다시 쓰는 편이 오히려 더 번거롭다.
- 한계(의도적으로 지원하지 않는 것): `$ref`와 정의 재사용, `oneOf`/`anyOf`/`allOf`, `pattern`/`format`,
  튜플 형태 `items`, 스키마를 값으로 받는 `additionalProperties`, enum의 객체·배열 비교.
  이보다 복잡한 스키마가 필요해지면 ajv로 갈아타는 게 맞고, 그 경계를 `parseSchema`가 명시적으로 지키고 있다.
- 한 가지 더: **선언한 type에서 의미가 없는 키워드도 거절한다**(예: `type: "number"`에 `minLength`).
  ajv는 통과시키지만, 그 규칙은 영원히 적용되지 않으므로 사용자는 검사했다고 착각하게 된다.

### 왜 모르는 키워드를 조용히 무시하지 않고 거절하는가

- 무시하면 "검사했는데 통과"라는 **거짓 결과**가 나온다. 검사 도구가 파는 것은 신뢰 하나뿐이고, 거짓 통과는 그 신뢰를 조용히 깨뜨린다.
- 거절은 시끄럽게 실패하는 선택이다. 사용자는 스키마를 고치거나 더 큰 도구를 쓰면 되고, 어느 쪽이든 결과를 오해하지 않는다.
- 같은 이유로 **타입을 강제 변환하지 않는다**. `"80"`을 80으로 바꿔 통과시키면, 정작 고쳐야 할 프롬프트나 모델 설정을 고치지 않게 된다.

### 왜 parseSchema와 validate를 나눴는가

- 두 오류의 **성격이 다르다**. 스키마 오류는 사람이 고칠 설정 파일 버그이고, 값 오류는 검사 결과(LLM 출력이 틀린 것)다.
  섞어 두면 CLI의 종료 코드와 출력 형식을 구분할 수 없다.
- `validate(value, schema: Schema)`는 `parseSchema`가 만든 타입만 받는다. 검증되지 않은 `unknown` 스키마로는
  호출 자체가 되지 않으므로, "스키마 검증 → 값 검증" 순서가 **타입으로 강제**된다.
- 덕분에 `validate`는 스키마 모양을 다시 의심하지 않아도 되어 구현이 단순해진다(옵션 키워드의 존재 여부만 본다).

### 오류 위치 규칙

- 위치는 JSON Pointer(RFC 6901)로 주고, **루트는 빈 문자열**이다. 키에 `/`나 `~`가 있으면 `~1`, `~0`으로 이스케이프한다.
- `required` 오류의 경로는 부모 객체가 아니라 **없는 그 필드**를 가리킨다(`/feedback`). 사용자가 손댈 위치가 그 필드이기 때문이다.
- 타입이 틀린 노드는 하위 규칙을 더 검사하지 않는다. 타입이 다른 값에 길이·범위 오류를 겹쳐 보고하면 원인이 가려진다.
- 그 외에는 첫 오류에서 멈추지 않고 전부 모은다. 한 번 돌려서 고칠 곳을 다 보는 게 목적이다.

## 13. CLI 설계(`src/commands/validate.ts`, `src/cli.ts`)

### 왜 종료 코드를 0/1/2로 나눴는가

- CI에서 두 실패는 대응이 완전히 다르다. **1은 LLM 출력이 기준에 못 미친 것**(프롬프트·모델·입력을 본다),
  **2는 도구를 잘못 쓴 것**(스키마·경로·인자를 본다). 둘을 같은 1로 묶으면 파이프라인이
  "모델 품질이 떨어졌다"와 "설정이 깨졌다"를 구분할 수 없고, 그 구분이야말로 자동화에서 제일 쓸모 있는 정보다.
- 2는 "**판정을 내리지 못했다**"는 뜻이다. 판정하지 못한 상태를 통과(0)로도 실패(1)로도 보고하지 않는 것이 중요하다.
  스키마에 모르는 키워드가 있을 때 1이 아니라 2인 이유가 이것이다(11·12번 절의 "거짓 통과를 만들지 않는다"와 같은 원칙).
- 관례와도 맞다. 린터·테스트 러너는 보통 1을 "검사 실패", 2 이상을 "실행 자체 실패"로 쓴다.
  일관성을 위해 `llm-check --nope`처럼 전역 인자가 잘못된 경우도 2로 맞췄다(이전 단계에서는 1이었다).

### 왜 stdout과 stderr를 나누는가

- **stdout은 판정, stderr는 도구 오류**로 고정했다. 그래서 `llm-check validate ... --json | jq` 같은 조합이 성립한다.
  종료 코드가 2일 때 stdout은 비어 있으므로, 스크립트가 깨진 JSON을 파싱하는 일이 생기지 않는다.
- `--json`은 종료 코드 0·1에서만 JSON을 낸다. 2에서는 사람이 읽을 메시지를 stderr로만 낸다.
  판정이 없는 상황에 판정 모양의 JSON을 주면 스크립트가 `ok: false`를 "모델 출력 문제"로 오해한다.

### 왜 io를 주입하는 구조로 만들었는가

- `runValidate(args, io) -> { exitCode, stdout, stderr }`는 부수효과가 없다.
  테스트는 메모리 `Record<string, string>` 하나로 "파일 없음", "스키마 JSON 깨짐", "stdin 입력"까지 전부 재현한다.
  임시 디렉터리를 만들고 지우거나 프로세스를 띄울 필요가 없어서, 명령 전체 테스트가 수십 ms에 끝난다.
- `process.exit`도 `console`도 쓰지 않으므로 **종료 코드와 출력이 반환값으로 검증된다**.
  실제 `fs`/`process` 연결은 `src/cli.ts` 한 파일에만 있고, `src/core`에는 Node 전용 코드가 전혀 없다(7번 절).
- 부수효과를 진입점으로 밀어낸 덕에, 나중에 다른 진입점(라이브러리 export, GitHub Action)에서 같은 로직을 재사용할 수 있다.
- `src/cli.ts`는 `process.exit()` 대신 `process.exitCode`만 설정한다.
  출력을 파이프로 보낼 때 `exit()`는 아직 다 쓰이지 않은 stdout을 잘라먹을 수 있다.

### 왜 --json 출력을 따로 두는가

- 사람용 출력은 정렬·여백·문구가 언제든 바뀐다. 스크립트가 그것을 파싱하면 문구를 고칠 때마다 깨진다.
  기계용 형식을 분리해 두면 사람용 출력을 자유롭게 다듬을 수 있다.
- 종료 코드만으로는 "무엇이 왜 틀렸는지"를 모은다. `errors[].path`/`keyword`가 있으면 PR 코멘트나 통계로 바로 쓸 수 있다.
- 결과에 `extract`(whole/scan, start, end)를 같이 담는 이유: 추출이 통째로 됐는지 잘라냈는지, 원문 어디를 잘라냈는지는
  프롬프트를 고칠 때 쓰는 정보다. 값 자체(`value`)는 넣지 않았다. 입력 파일을 그대로 다시 출력하는 셈이라 의미가 없다.

### 왜 E2E를 Vitest가 아니라 CI 셸 스텝에 뒀는가

- 단위 테스트는 `runValidate`까지만 본다. 그 바깥의 세 가지는 아무도 검증하지 않는다:
  번들된 `dist/cli.js`가 실제로 실행되는지(shebang·ESM·`../package.json` 경로), `src/cli.ts`의 라우팅과 `process.exitCode`,
  그리고 `examples/`가 README에 적어 둔 출력과 여전히 일치하는지.
- 그 검증은 **빌드 산출물**을 필요로 한다. Vitest에서 `dist/cli.js`를 띄우면 `npm run test`가 빌드를 전제하게 되고,
  결국 `npm run check`가 `npm run build`를 먼저 요구한다. 지금 `check`는 빌드 없이 도는 **빠른 검사**이고(9번 절),
  CI와 로컬에서 같은 한 줄로 끝나는 게 그 가치다. 그 결합을 만들지 않으려고 E2E는 `runtime-floor` job의 셸 스텝에 뒀다.
- 그 job은 이미 빌드를 하고 Node 20으로 바꿔 둔 상태다. 그래서 E2E가 "종료 코드 규약 검증"과 "engines 하한에서의 실행 검증"을
  한 번에 겸한다. 파일도 늘지 않는다.
- 스크립트를 쓸 때 주의한 것: GitHub Actions의 `run`은 `bash -e`로 실행된다.
  `명령; test $? -eq 1`은 앞 명령이 0이 아닌 순간 스텝이 죽어서 비교에 도달하지 못하고,
  `! 명령`은 1과 2를 구분하지 못한다(둘 다 "0이 아님"이다). 종료 코드를 꼭 구분해야 하므로
  `code=0; 명령 || code=$?` 로 받아서 기대값과 정확히 비교하고, 틀리면 어느 예시가 몇으로 끝났는지 출력한 뒤 마지막에 한 번 실패시킨다.

## 14. 정의문 복사 판정(`src/core/overlap.ts`, `src/commands/overlap.ts`)

출처: MetaLearn의 `backend/app/features/curriculum/retrieval_level.py`.
LLM에게 빈칸 문항과 문항 유형 라벨(kind)을 함께 받았는데, 라벨을 직접 확인해 보니 13개 중 6개가 실제와 달랐다
(정의문을 그대로 옮겼는데 "상황"이라고 신고). 그래서 라벨을 믿지 않고 기계로 재기로 했고,
이 판정기로 재니 19개 중 12개가 정의문을 되읽는 문항이었다. 판정 방식은 원본 그대로 옮겼다(바꾸면 그때 쟀던 수치와 비교할 수 없다).

### 왜 글자 2-gram 집합 겹침인가, 그리고 왜 방향이 있는가

- 형태소 분석기나 임베딩을 쓰면 의존성과 모델이 따라온다. 이 도구는 오프라인에서 돌아야 하고 런타임 의존성이 0이다(3번 절).
  글자 2-gram은 한국어에서 조사·어미 변화("설계한다" / "설계하는" / "설계 방식")를 상당 부분 흡수하면서 구현이 20줄이다.
- 1-gram은 글자만 같아도 겹치고(의미 없이 비율이 올라간다), 3-gram 이상은 어미가 조금 바뀌면 급격히 떨어진다.
  재사용 여부만 보는 데는 2-gram이 둔감함과 민감함의 균형점이었다.
- **집합**으로 세는 이유: 같은 2-gram이 여러 번 나오는 것을 세면 긴 문항에서 비율이 왜곡된다. 등장 여부만 본다.
- **방향이 있는 이유**: 분모가 정의문의 2-gram 수다. 즉 "정의문이 문항에 얼마나 담겼는지"를 잰다.
  반대 방향(`overlap(문항, 정의문)`)은 "문항이 정의문 안에 있는지"가 되어, 정의문을 그대로 옮긴 **긴** 문항에서 값이 낮게 나온다.
  우리가 잡으려는 것은 "정의문이 문항 안에 통째로 들어 있는가"이므로 정의문이 분모여야 한다.
  테스트에서 `overlap("최상위 컴포넌트", "최상위 컴포넌트를 먼저 설계한다") === 1`이고 그 반대는 1보다 작은 것으로 이 방향성을 고정했다.

### threshold 0.6의 출처와 한계

- MetaLearn에서 실제 생성된 문항의 분포를 보고 고른 값이다. 정의문을 옮긴 문항은 0.9 이상, 다른 말로 바꾼 문항은 0.1 안팎으로
  두 덩어리가 꽤 멀리 떨어져 있었고, 0.6은 그 사이의 빈 구간이다(이 저장소 `examples/questions.json`에서도 0.97과 0.06으로 갈린다).
- **한계: 이 값은 그 데이터에서만 검증됐다.** 과목·문항 길이·정의문 길이가 달라지면 분포가 달라지므로 다시 정해야 한다.
  그래서 `--threshold`로 밖에서 바꿀 수 있게 열어 두고, 기본값을 코드와 README·DECISIONS 세 곳에 같이 적어 두었다.
  경계값(정확히 threshold면 copied)도 테스트로 고정했다. 임계값을 바꿀 때 어느 쪽이 포함되는지 헷갈리면 안 되기 때문이다.
- 비율은 소수점 넷째 자리에서 반올림해 출력한다. `0.9696969696969697`을 그대로 내보낼 이유가 없고, 판정은 이미 반올림 전 값으로 끝났다.

### 왜 잴 수 없으면 강등하지 않는가

- 정의문이나 문항이 비어 있으면(또는 글자가 하나도 없으면) 비율을 계산할 근거가 없다. 이때 `copied`로 처리하면 **거짓 신고**가 되고,
  `ok`로 처리하면 **거짓 통과**가 된다. 둘 다 틀리므로 `unmeasurable`이라는 제3의 상태를 두고 개수만 보고한다.
- 판별 유니온이라 `unmeasurable`에는 `ratio` 키 자체가 없다. "0으로 쟀다"와 "재지 못했다"가 타입에서 구분된다(12번 절의 `start`와 같은 이유).
- 종료 코드는 `copied` 개수만 본다. 잴 수 없는 문항이 많으면 그건 입력 데이터 문제이고, 사람이 출력에서 보고 판단할 일이다.

### 원본에서 이번 범위에 넣지 않은 판정

- **객관식 구별(L3 판정)**: 원본은 보기(choices)가 있는 문항을 다르게 취급했다. 이 CLI의 입력 형식에는 보기가 없고,
  보기를 받기 시작하면 입력 스키마와 출력 형식이 함께 커진다. 지금 범위는 "빈칸 문항 하나와 정의문 하나"다.
- **여러 줄 걸침 판정**: 원본은 정의문이 여러 문장·여러 줄에 흩어진 경우를 따로 봤다. 그건 MetaLearn의 교재 데이터 구조에 맞춘 처리라서,
  범용 CLI에서는 입력을 어떻게 쪼개 줄지 사용자가 결정하는 편이 맞다(필요하면 문항을 나눠 여러 항목으로 넣으면 된다).
- 둘 다 "지금 쓰지 않는 기능을 미리 옮기지 않는다"는 판단이다. 필요해지면 입력 형식부터 다시 정하는 것이 순서다.

### Python 정규식과 JS 정규식의 차이

- 원본: `re.sub(r"[^\w가-힣]", "", text)`. 파이썬 3의 `\w`는 기본이 유니코드라 한글·한자·악센트 문자가 이미 포함되고,
  `가-힣`는 사실상 중복이었다(완성형 음절만 가리키므로 `\w`가 이미 덮는다).
- 이 구현: `/[^\p{L}\p{N}_]/gu`. `\w`의 유니코드 의미(문자 + 숫자 + 밑줄)를 그대로 풀어 쓴 것이다.
  JS의 `\w`는 유니코드 플래그와 무관하게 `[A-Za-z0-9_]`뿐이라 그대로 옮기면 한글이 전부 지워진다. 그래서 `\p{...}`를 쓴다.
- 남는 차이: 파이썬 `\w`는 밑줄과 일부 결합 문자(`Mn` 범주)를 포함하는데, `\p{L}\p{N}_`는 결합 문자를 포함하지 않는다.
  한글 완성형·영문·숫자로 이루어진 입력에서는 결과가 같고, 분해형 한글(NFD)이나 결합 악센트가 섞인 입력에서만 달라질 수 있다.
  LLM이 돌려주는 텍스트에서는 사실상 만나지 않아 지금은 받아들였다. 문제가 되면 `\p{M}`을 추가하면 된다.
- 2-gram을 셀 때는 `Array.from()`으로 **코드 포인트** 단위로 쪼갠다. 파이썬 `str` 순회가 코드 포인트 단위이므로 같은 결과가 나온다
  (`text[i]`로 돌면 UTF-16 코드 유닛이라 이모지·보조 평면 문자에서 달라진다).

## 15. 로컬 환경 주의: `NODE_ENV=production`

- 이 PC에는 `NODE_ENV=production`이 전역으로 설정돼 있어, 그대로 `npm install`하면 devDependencies가 설치되지 않는다
  (npm이 `omit=dev`로 동작). 빈 `node_modules`로 린트/테스트가 안 돌면 이걸 먼저 의심한다.
- 해결: `NODE_ENV=development npm install` 또는 `npm install --include=dev`.
- CI(GitHub Actions)에는 이 변수가 없으므로 영향이 없다.
